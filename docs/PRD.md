- 관련 문서: [MVP 일정](SCHEDULE.md), [서비스 기획서](SERVICE_SPEC.md)

> **요약**
> - 청약 입문자가 APT 분양 공고를 검색·필터로 찾고(1단계), 쉬운 요약으로 이해하고, 공고별 체크리스트로 자격 요건을 스스로 점검(2단계)하게 돕는다.
> - 공고 목록과 정형 데이터는 청약홈 Open API로, 자격 요건은 공고문 PDF에서 LLM으로 추출하며, 모든 요약 항목에 원문 근거를 단다.
> - 서비스는 자격을 판정하지 않고 안내만 한다.

## 1. 배경과 문제

청약 공고는 계속 새로 등록되고 정정되지만, 공고문 하나가 수십 페이지 분량이고 용어와 조건이 복잡하다.
청약에 익숙하지 않은 사용자는 다음 단계마다 막힌다.

1. **발견:** 어떤 공고가 새로 나왔는지, 무엇이 바뀌었는지 계속 확인해야 한다.
2. **이해:** 공고문의 핵심(일정, 공급 규모, 분양가, 자격 요건)을 파악하기 어렵다.
3. **판단:** "이 공고에 내가 신청할 수 있나?"를 스스로 판단하기 어렵다.

## 2. 목표

사용자가 공고문을 매번 직접 찾아 읽고 비교하지 않아도, **자신과 관련 있는 공고를 빠르게 발견하고, 쉬운 말로 이해하고, 신청 가능 여부를 스스로 점검**할 수 있게 한다.

**프로젝트 성격:** 포트폴리오이자 실제로 런칭하는 서비스다. 기술 깊이(수집 파이프라인, PDF·LLM 추출, 원문 근거 표시)와 운영에 필요한 최소한의 안정성·개인정보 보호를 함께 갖춘다.

## 3. 대상 사용자

**주 사용자: 청약 입문자**
- 사회초년생, 신혼부부 등 청약을 처음 알아보는 사람
- '특별공급', '해당지역 우선', '무주택세대구성원' 같은 용어부터 낯설다.
- 원하는 것: "나와 관련 있는 공고가 뭔지", "이 공고가 무슨 내용인지", "나도 신청할 수 있는지"

**MVP에서 우선순위가 낮은 사용자:** 이미 청약을 잘 아는 사람. 이들에게는 빠른 알림과 비교가 핵심이며, 이 니즈는 MVP 이후에 강화한다.

## 4. 핵심 설계 원칙

| 원칙 | 내용 |
|---|---|
| **판정이 아니라 안내** | 서비스는 "당신은 자격이 됩니다"라고 단정하지 않는다. 사용자가 원문을 바탕으로 스스로 판단하도록 돕는다. |
| **모든 요약에 원문 근거 표시** | 공고 요약·요건 항목마다 공고문의 해당 페이지와 문구를 연결해, 사용자가 언제든 원문으로 확인할 수 있게 한다. |
| **2단계 판단 구조** | 1단계(공고 찾기)에서는 사용자가 검색·필터로 관심 있는 공고를 직접 추린다. 2단계(자격 점검)에서는 고른 공고 하나의 자격 요건을 질문 형태로 보며 직접 체크한다. |
| **공식 API 우선** | 공고 목록과 정형 데이터는 공식 Open API로 받는다. 스크래핑은 공고문 PDF 수집처럼 꼭 필요한 곳에만 쓴다. |

## 5. MVP 범위

### 포함
- **공고 종류:** 청약홈(한국부동산원)의 **APT 분양 공고**
  - 민영주택, 국민주택
  - 무순위·잔여세대 (무순위, 불법행위 재공급)
- **알림 채널:** 이메일 (F7, 후순위)

### 제외 (향후 확장 후보)
- LH·SH 등 공공임대(행복주택, 국민임대, 매입임대)
- 오피스텔·도시형생활주택 등 APT 외 공고
- 카카오톡 알림톡, 웹 푸시, 모바일 앱
- 가점 계산기 (청약홈에 이미 있음)
- 프로필 입력과 프로필 기반 맞춤 공고 추천
- 사용자 정보만으로 자격을 자동 판정하는 기능

## 6. 기능 요구사항

**우선순위:** 필수 = 런칭 조건 / 중요 = 런칭 전 목표 / 후순위 = 일정이 밀리면 런칭 이후로 미룸

| 기능 | 우선순위 |
|---|---|
| F1. 공고 수집·갱신 | 필수 |
| F2. 공고 요약 (원문 근거 포함) | 필수 |
| F3. 검색·필터링 | 필수 (F3-11 조건 저장은 후순위) |
| F4. (삭제) | - |
| F5. 공고별 자가진단 | 중요 |
| F6. 원문 확인 | 필수 |
| F7. 관심 조건 알림 | 후순위 |

### F1. 공고 수집·갱신
| ID | 요구사항 |
|---|---|
| F1-1 | 공공데이터포털 「한국부동산원_청약홈 분양정보 조회 서비스」 API로 APT 공고와 무순위·잔여세대 공고를 주기적으로 수집한다. |
| F1-2 | 공고별 주택형 정보(주택형·전용면적, 공급면적, 일반·특별공급 세대수, 특별공급 유형별 세대수, 최고 분양가)를 함께 수집한다. 공고 유형에 따라 API에 없는 항목이 있다(7장). |
| F1-3 | 공고문 PDF를 수집해 저장한다. |
| F1-4 | 신규 공고를 감지한다. |
| F1-5 | 변경·정정된 공고를 감지한다. (감지 방식은 8장) |
| F1-6 | 변경이 감지되면 요약과 요건 추출을 다시 수행하고, 무엇이 바뀌었는지 기록한다. |

### F2. 공고 요약 (원문 근거 포함)
| ID | 요구사항 |
|---|---|
| F2-1 | 공고마다 핵심 정보를 한눈에 보여준다: 위치, 공급 규모, 주택형별 분양가, 주요 일정(특별공급, 1·2순위 접수, 당첨자 발표, 계약), 규제 지역 여부. |
| F2-2 | 공고문 PDF에서 자격 요건(특별공급 유형별 조건, 소득·자산 기준, 거주지 우선순위, 무주택 요건, 청약통장 요건 등)을 구조화해 추출한다. |
| F2-3 | 추출한 항목마다 원문의 페이지 번호와 근거 문구를 함께 저장하고 보여준다. |
| F2-4 | 어려운 청약 용어와 특별공급 유형에 쉬운 말 설명을 붙인다(예: 신혼부부 = 혼인 기간 7년 이내). 공고 원문이 아닌 일반 설명이므로 "공고마다 다를 수 있음"을 표시하고 출처(주택공급에 관한 규칙 등)를 단다. |
| F2-5 | "최종 확인은 원문 공고문으로 해야 한다"는 안내를 요약 화면에 항상 표시한다. |
| F2-6 | 공고 상세에 정정 이력과 마지막 확인 시각을 표시한다. |

### F3. 검색·필터링 (1단계: 공고 찾기)

**필터 조건**

| ID | 조건 | 요구사항 |
|---|---|---|
| F3-1 | 지역 | 공급지역(시·도) 기준. 여러 지역을 함께 고를 수 있다. |
| F3-2 | 주택 구분 | 민영주택 / 국민주택 |
| F3-3 | 공고 유형 | 일반 분양 / 무순위 / 불법행위 재공급. 일반 분양은 호출한 API로, 나머지 둘은 무순위·잔여세대 API의 주택 구분 값으로 구분한다. |
| F3-4 | 접수 상태 | 접수 예정 / 접수 중 / 마감. 첫 접수 시작일 ~ 마지막 접수 종료일 = 접수 중. 일반 분양은 특별공급(없으면 1순위) 시작일부터 2순위 종료일까지, 무순위는 해당 공고의 접수 기간을, 불법행위 재공급은 특별공급·일반공급 일정이 있으면 일반 분양과 같은 방식으로, 없으면 접수 기간을 쓴다. 기본 선택은 접수 예정 + 접수 중이다. |
| F3-5 | 특별공급 유형 | 신혼부부, 생애최초, 다자녀, 노부모, 청년, 신생아 등. 고른 유형의 세대수가 1 이상인 주택형이 있는 공고. 유형마다 F2-4 설명을 붙인다. |
| F3-6 | 분양가 범위 | 주택형별 최고 분양가 기준 |
| F3-7 | 전용면적 범위 | 주택형별 전용면적 기준(예: 59㎡, 84㎡). 공급면적은 무순위 공고에 없어서 모든 공고에 같은 기준을 쓸 수 있는 전용면적을 쓴다. |
| F3-8 | 단지명 검색 | 단지명(주택명) 부분 일치 |

- **정보가 없는 공고:** 무순위·잔여세대 공고(무순위, 불법행위 재공급)에는 주택 구분(F3-2)과 특별공급 유형별 세대수(F3-5) 정보가 없다. 이 필터를 고르면 해당 공고는 결과에서 빠지고, 목록 위에 "정보가 없어 제외된 무순위·잔여세대 공고 N건"을 안내한다.

**목록 동작**

| ID | 항목 | 요구사항 |
|---|---|---|
| F3-9 | 조건 조합 | 서로 다른 조건은 AND, 한 조건 안의 여러 값은 OR로 결합한다. 주택형 단위 조건(F3-5~F3-7)은 **같은 주택형**이 모두 만족해야 한다. |
| F3-10 | 정렬 | 기본은 접수 임박순: 접수 중(종료일 가까운 순) → 접수 예정(시작일 가까운 순) → 마감. 모집공고일 최신순도 고를 수 있다. 세부 규칙은 [서비스 기획서 S-01](SERVICE_SPEC.md#s-01-공고-목록-홈). |
| F3-11 | 조건 저장 (후순위) | 현재 필터 조건을 저장해 다시 불러온다. 저장 방식은 미해결 질문 5와 함께 정한다. |

### F5. 공고별 자가진단 (2단계: 자격 점검)
| ID | 요구사항 |
|---|---|
| F5-1 | 공고에서 추출한 자격 요건을 쉬운 예/아니오 질문 형태의 체크리스트로 보여준다. |
| F5-2 | 체크리스트 항목마다 원문 근거(페이지·문구)를 연결한다. |
| F5-3 | 사용자의 응답에 따라 지원을 검토해 볼 만한 공급 유형(특별공급 유형, 일반공급 순위)을 정리해 보여준다. 단, 최종 판정이 아니라는 점을 명시한다. |

### F6. 원문 확인
| ID | 요구사항 |
|---|---|
| F6-1 | 공고마다 원본 공고문(PDF)과 청약홈 공고 페이지 링크를 제공한다. |
| F6-2 | 요약·체크리스트에서 근거를 누르면 원문의 해당 페이지로 이동한다. |

### F7. 관심 조건 알림
| ID | 요구사항 |
|---|---|
| F7-1 | F3-11로 저장한 필터 조건을 알림 조건으로 쓴다. |
| F7-2 | 알림 조건에 맞는 신규 공고가 등록되면 이메일로 알린다. |
| F7-3 | 관심 공고가 정정되면 무엇이 바뀌었는지와 함께 이메일로 알린다. |
| F7-4 | 이메일에서 알림을 쉽게 해지할 수 있다. |

## 7. 데이터 출처 (조사 결과)

**공식 API:** 「한국부동산원_청약홈 분양정보 조회 서비스」 (https://www.data.go.kr/data/15098547/openapi.do)
- REST(JSON/XML), `serviceKey` 인증, 무료
- 개발계정 트래픽 40,000건. 운영계정은 활용사례를 등록하면 늘릴 수 있다.
- 호출 주소: `https://api.odcloud.kr/api/ApplyhomeInfoDetailSvc/v1/<오퍼레이션>`
  - 인증키는 Decoding 키를 URL 인코딩해 `serviceKey`로 넘긴다(Encoding 키를 다시 인코딩하면 인증 오류).
  - 페이지는 `page`, `perPage`(1,000까지 동작 확인)로 넘기고, 조건은 `cond[필드::EQ|GTE|LTE]`로 서버에서 거른다.
  - 응답 형태: `{ page, perPage, totalCount, matchCount, currentCount, data: [...] }`
- 사용할 오퍼레이션
  - `getAPTLttotPblancDetail` / `getAPTLttotPblancMdl`: APT 공고 / 주택형별 정보 (주택형별은 `cond[HOUSE_MANAGE_NO::EQ]`로 공고와 연결)
  - `getRemndrLttotPblancDetail` / `getRemndrLttotPblancMdl`: 무순위·잔여세대 공고 / 주택형별 정보 (APT와 다른 점은 아래 "무순위·잔여세대 API 차이")
- **공고 키:** `HOUSE_MANAGE_NO`(주택관리번호). 2026-10-17 기준 전체 APT 공고 2,907건에서 `PBLANC_NO`와 항상 같고 중복이 없다. 무순위·잔여세대 공고 1,718건도 같고, APT 공고와 겹치는 번호가 없다(무순위 `…910…`, 불법행위 재공급 `…930…` 대역). 그래서 두 API의 공고를 한 테이블에 저장할 수 있다.
- **API로 받을 수 없는 것:** 자격 요건(소득 기준, 거주지 우선, 특별공급 세부 조건)은 공고문 PDF에만 있다.
- **정정 공고:** 수정일시나 정정 여부 필드가 없다. 정정되면 같은 공고번호에서 공고문 PDF만 바뀌고, API 값은 그대로일 수 있다(아래 "정정 공고 확인 결과").

**공고문 PDF 받는 경로 (2026-10-17 확인, 무순위·잔여세대는 2026-10-19 확인)**

`PBLANC_URL`은 PDF가 아니라 청약홈 상세 페이지(HTML)다. PDF는 두 단계로 받는다.

1. `PBLANC_URL`(상세 페이지)을 받아 "모집공고문 보기" 링크를 찾는다.
2. 링크(`https://static.applyhome.co.kr/ai/aia/getAtchmnfl.do?houseManageNo=…&pblancNo=…&atchmnflSeqNo=…&atchmnflSn=…`)로 PDF를 받는다.

- 첨부파일 번호(`atchmnflSeqNo`, `atchmnflSn`)는 API에 없어서 1단계가 꼭 필요하다.
- 로그인이나 세션 쿠키 없이 받을 수 있다.
- 응답 `Content-Type`이 `application/octet-stream`이므로, PDF 여부는 `Content-Disposition` 파일명이나 파일 첫 바이트(`%PDF`)로 판별한다.
- 무순위·잔여세대 공고도 상세 페이지(`selectAPTRemndrLttotPblancDetailView.do`)에 같은 형식의 "모집공고문 보기" 링크가 있다.
- **신혼희망타운(LH 공공분양)은 청약홈에 PDF가 없다.** APT API에 `HOUSE_SECD_NM` "신혼희망타운"(`…820…` 대역)으로 섞여 나오지만, 상세 페이지에는 LH청약플러스 링크만 있다. 2026-10-19 스냅샷 48건 중 2건이다. 이런 공고는 PDF 없이 기본 정보와 원문 링크만 보여 준다(PDF 추출 실패와 같은 처리).
- 정정된 공고는 PDF 파일명 앞에 `(2026.10.19.정정)`처럼 정정일이 붙는다.

**정정 공고 확인 결과 (2026-10-19)**

10-17 스냅샷과 같은 조건(모집공고일 2026-09-01 이후 APT 공고 48건)으로 다시 받아 비교했다(`experiments/correction_check/recheck.py`, 결과는 `docs/api-samples/snapshot_2026-10-19.json`).

- **API 값이 바뀐 공고는 0건이었다.** 그런데 `2026000507`(광안센텀 비스타동원)은 10-19에 정정 공고가 나왔고, PDF 내용(해시)이 10-18에 받은 파일과 달랐다. 정정해도 API 값은 그대로이고 PDF만 바뀔 수 있다.
- PDF가 있는 46건 중 6건(13%)의 파일명에 정정 표기가 있었다. 모두 원래 공고번호 그대로였고, 정정 공고가 새 번호로 등록된 경우는 없었다. 10-17에 받은 전체 APT 공고 2,907건에서도 단지명에 "정정·변경" 표기가 붙은 공고는 없었고, 단지명이 같은 공고 37묶음은 모두 36일 이상 간격의 재공급(추가모집 등)이었다. **결론: 정정 공고는 같은 번호로 덮어쓴다.**
- 정정 PDF는 첫 쪽에 정정 안내 상자("변경 전 / 변경 후" 또는 "당초 / 정정")를 넣는다. 이 상자 때문에 뒤쪽의 쪽 번호가 밀린다(2026000507은 44쪽 → 45쪽).

## 8. 기술 고려사항

- **PDF → 구조화 추출 파이프라인이 서비스의 핵심이다.** 사람이 검수하지 않고 자동으로 운영하므로 다음을 지킨다.
  - 파싱할 때 페이지와 위치 정보를 유지해야 원문 근거를 표시할 수 있다.
  - LLM이 각 항목의 근거(페이지·문구)를 함께 출력하도록 추출 스키마를 정의한다.
  - 근거 문구가 실제로 원문에 있는지 문자열 매칭으로 검증하고, 근거가 확인되지 않는 항목은 표시하지 않거나 "확인 필요"로 표시한다.
- **공고문 PDF 형식 (2026-10-19, 스냅샷 공고 46개 조사):**
  - **모두 텍스트 PDF다.** 이미지 스캔 PDF는 없었다. 글자가 거의 없는 쪽은 5개 파일에서 1쪽씩(지도·도장 등 마지막 쪽)뿐이다.
  - 분량은 25~95쪽(중앙값 65쪽)이다. 무순위·불법행위 재공급은 16~20쪽으로 짧다.
  - 40개는 한글(HWP)에서 만든 PDF이고 텍스트 순서가 대체로 자연스럽다. **6개(13%)는 "Microsoft: Print To PDF"로 만들어져 텍스트 순서가 깨진다**(예: "2년 이상 계속 거주자"가 "년 이상 계속 거주자 2"로 추출됨). 이런 파일은 텍스트만 뽑아 파싱하면 숫자를 잘못 읽고, 근거 문구의 문자열 검증도 실패하기 쉽다.
- **파싱 방식:** 텍스트를 직접 뽑아 규칙으로 파싱하지 않고, PDF를 그대로 Claude에 넣고 citations로 쪽 번호와 인용 문구를 받는다(`experiments/pdf_extraction/extract.py`). 모델이 쪽 이미지도 함께 보므로 표와 텍스트 순서가 깨진 파일에도 대응할 수 있다. 근거 검증은 공백을 무시하고 비교하며, 요건의 숫자가 인용 문구에 있는지도 검사한다.
  - 비용(claude-opus-5-5, 입력 $4/MTok): 쪽당 약 3,700~5,200 토큰이다. 16쪽 공고는 입력 6만 토큰에 출력 포함 $0.41, 48쪽 25만 토큰, 95쪽 36만 토큰이다. 일반 APT 공고 1건에 입력만 약 $1~1.5가 든다. 비용을 줄이려면 자격 요건이 있는 쪽만 골라 넣는 방법을 검토한다.
  - 1차 결과(무순위 1건): 숫자·조건 오류는 없었지만, 일반 규정(「주택공급에 관한 규칙」을 옮긴 정의·예외 목록)까지 항목마다 뽑고 문장을 길게 옮기는 문제가 있었다(`experiments/pdf_extraction/REVIEW_2026910220.md`). 특별공급·소득 기준이 있는 일반 APT 공고로 다시 확인해야 한다.
- **정정 공고 감지:** API에 수정일시 필드가 없으므로, 최근 N일 범위를 주기적으로 다시 조회하고 공고 키별 레코드 해시를 비교한다. 공고마다 버전 이력을 남긴다.
  - API 값은 그대로이고 PDF만 바뀌는 정정이 있으므로(7장), **공고문 PDF의 파일 해시도 함께 비교한다.** 상세 페이지의 첨부파일 번호나 파일명의 정정 표기는 보조 신호로만 쓴다.
  - 정정 PDF는 앞쪽에 정정 안내가 들어가 쪽 번호가 밀리므로, 이전 버전의 근거(쪽 번호)를 재사용하지 않고 요건 추출을 처음부터 다시 한다(F1-6).
  - "무엇이 바뀌었는지"(F2-6, F7-3)는 정정 PDF 첫 쪽의 정정 안내 상자(변경 전/후)에서 뽑을 수 있다. 두 버전의 추출 결과를 비교하는 것보다 정확하다.
- **개인정보:** MVP에서는 프로필을 받지 않는다. 자가진단 응답(결혼 여부, 무주택 여부, 소득 등)은 민감하므로 저장하지 않고 자가진단 중에만 쓰는 방식을 검토한다.
