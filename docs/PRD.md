# PRD: 청약 공고 알림·점검 서비스 "청담"

- 작성일: 2026-10-06 / 수정일: 2026-10-20
- 상태: 초안
- 범위: MVP
- 관련 문서: [서비스 기획서](SERVICE_SPEC.md), [기술 노트](TECH_NOTES.md), [MVP 일정](SCHEDULE.md)

> **요약**
> - 청담은 청약 입문자가 APT 분양 공고를 **놓치지 않고, 신청한 뒤 후회하지 않게** 돕는다.
> - 놓치지 않게: 저장한 조건에 맞는 새 공고와 정정 공고를 이메일로 알리고, 접수·계약 일정을 캘린더에 넣게 한다.
> - 후회하지 않게: 신청 전에 공급 유형별 자격 조건과 "당첨되면 생기는 제약"을 원문 근거와 함께 보여 준다.
> - 서비스는 자격을 판정하지 않는다. 모든 정보에 원문 근거를 달고 최종 확인은 원문으로 하게 한다.

## 1. 목표

### 1.1 해결하려는 문제

청약 공고는 계속 새로 올라오고 정정되지만, 공고문 하나가 25~95쪽(중앙값 65쪽)이고 용어와 조건이 복잡하다. 청약을 처음 해 보는 사람은 두 지점에서 손해를 본다.

1. **놓친다.** 새 공고를 매일 확인하지 않으면 모르고 지나간다. 공고가 올라온 뒤 첫 접수까지 중앙값 10일, 첫 접수에서 계약까지 다시 중앙값 21일이 걸리고, 그 사이에 공급 유형별 접수일이 여러 번 있다. 공고를 봐 두고도 접수일이나 계약일을 잊는다. 최근 공고의 13%는 정정됐는데, 정정은 공고문 PDF에만 반영되어 알아채기 어렵다.
2. **신청하고 후회한다.** 입문자는 "일단 넣고, 당첨되면 자세히 읽는다." 그런데 당첨된 뒤 자금이나 사정 때문에 포기하면 재당첨 제한 같은 제약을 받을 수 있고, 자격이 안 되는데 당첨되면 일정 기간 청약이 제한된다. 이런 내용은 공고문 깊숙이 있다.

(수치 출처: 2026-10-19 스냅샷, 모집공고일 2026-09-01 이후 APT 공고 48건. [기술 노트 1장](TECH_NOTES.md#1-데이터-출처-조사-결과))

### 1.2 제품 목표

사용자가 청약홈을 매일 들여다보지 않아도 **나에게 맞는 공고와 그 정정을 놓치지 않고**, 신청하기 전에 **넣을 수 있는지(자격)와 넣어도 괜찮은지(당첨 후 제약)를 원문 근거와 함께 스스로 확인**하게 한다.

### 1.3 기대 효과

| 대상 | 효과 |
|---|---|
| 사용자 | 공고·정정·접수일을 놓치는 일이 줄어든다. 당첨 후 감당하지 못할 공고에 무심코 넣는 일이 줄어든다. 공고문 전체를 읽지 않고도 판단에 필요한 부분만 근거와 함께 본다. |
| 팀 (프로젝트) | 공공 데이터 수집 파이프라인, PDF·LLM 근거 추출, 정정 감지라는 기술 깊이를 실제로 운영되는 서비스로 증명한다. 실제 사용자 반응으로 가설(4장)을 검증한다. |

### 1.4 성공 지표

런칭에서는 아래 4개만 잰다. 목표값은 소수 사용자 공개(6주차) 결과를 보고 정한다.

| 지표 | 확인하려는 것 | 관련 기능 |
|---|---|---|
| 방문 수 | 서비스가 발견되는가 | 전체 |
| 알림 구독 수 | "놓치지 않게"에 사람들이 가치를 느끼는가 | F3-11, F7 |
| 알림 메일 클릭률 | 알림이 실제로 행동으로 이어지는가 | F7 |
| 요건 추출 성공률 | 공고 상세가 근거 있는 정보로 채워지는가 | F2, F5, F8 |

## 2. 대상 고객

### 2.1 주 사용자: 청약 입문자

- 사회초년생, 신혼부부 등 청약을 처음 알아보는 사람.
- '특별공급', '해당지역 우선', '무주택세대구성원' 같은 용어부터 낯설다.
- 청약홈을 매일 확인하지 않는다. 공고를 알게 되면 "일단 넣어 보자"고 생각하고, 세부 내용은 당첨된 뒤에 읽으려 한다.
- 원하는 것: "나와 관련 있는 공고가 나오면 알려 줘", "넣기 전에 이것만은 알고 넣자"

### 2.2 페르소나

| 페르소나 | 상황 | 청담에서 얻는 것 |
|---|---|---|
| **지원** (29세, 서울, 미혼, 무주택) | 청약통장은 5년 전에 만들었지만 써 본 적이 없다. "생애최초"가 자기에게 해당하는지 모른다. | 서울·경기 생애최초 조건을 저장해 두고 새 공고 메일을 받는다. 상세에서 생애최초 조건표를 하나씩 체크하고, 접수일을 캘린더에 넣는다. |
| **하늘** (33세, 경기, 결혼 2년 차, 맞벌이) | 신혼부부 특별공급은 알지만 맞벌이 소득 기준이 헷갈린다. 당첨되면 계약금을 낼 수 있을지 걱정한다. | 신혼부부 조건표에서 소득 기준을 원문 표로 확인한다. "당첨되면 이렇게 돼요" 카드에서 계약금 비율과 전매제한·실거주 의무를 보고 넣을지 정한다. |

페르소나의 행동에서 뽑은 화면 규칙은 [서비스 기획서 2.3](SERVICE_SPEC.md#23-흐름에서-뽑은-기획-포인트)에 있다.

### 2.3 우선순위가 낮은 사용자

- **청약을 잘 아는 사람:** 빠른 알림과 공고 비교를 원한다. 알림은 MVP로도 쓸 수 있지만, 비교 기능은 MVP 이후에 다룬다.
- **공공임대(LH·SH) 대상자:** 입문자에게 현실적인 선택지가 많지만 데이터 출처가 달라 MVP 이후에 다룬다.

## 3. 전략적 적합성

청담은 2명이 파트타임으로 만드는 프로젝트이며, **포트폴리오이자 실제로 런칭하는 서비스**다. 이 제품은 두 목적을 함께 만족한다.

| 프로젝트 전략 | 청담이 그것을 지원하는 방식 |
|---|---|
| 기술 깊이를 보여 준다 | 공식 API 수집과 증분 갱신, 공고문 PDF에서 LLM으로 요건을 뽑고 인용 문구를 원문과 문자열로 대조하는 검증, API에 드러나지 않는 정정을 PDF 해시로 감지하는 파이프라인. 각각 실험으로 실현 가능성을 확인했다([기술 노트](TECH_NOTES.md)). |
| 실제 사용자에게 쓰인다 | 데모용이 아니라 매일 수집하고 알림을 보내는 운영 서비스로 만든다. 알림 구독 수와 클릭률로 실제 가치를 확인한다. |
| 작은 팀으로 끝까지 해낸다 | 근본 역할을 "놓치지 않고, 후회하지 않게"로 좁히고, 그 역할을 만들지 않는 기능(질문형 자가진단, 용어 사전 화면, 세부 이벤트 측정)은 뺐다. |

**지금 할 만한 이유**

- 청약홈 분양정보 API가 무료로 공개되어 있고, 공고 목록·일정·주택형별 세대수와 분양가를 받을 수 있다.
- 공고문 PDF는 모두 텍스트 PDF였고(조사 46건), PDF를 Claude에 그대로 넣으면 쪽 번호와 인용 문구가 붙은 요건을 받을 수 있음을 실험으로 확인했다.
- 자격 요건과 당첨 후 제약은 공고문 PDF에만 있다. 이것을 근거와 함께 정리해 주는 일이 API만 가공하는 서비스와의 차이다.

## 4. 우리의 신념

검증해야 할 가설이다. 각 가설이 틀리면 어떤 기능이 흔들리는지와 확인 방법을 함께 적는다.

| ID | 신념 | 근거 | 흔들리는 기능 | 확인 방법 |
|---|---|---|---|---|
| H1 | 입문자는 공고를 매일 확인하지 않는다. 알려 주지 않으면 놓친다. | 팀원의 실제 경험. 공고→접수 중앙값 10일, 접수일이 유형별로 여러 번이다. | F7 알림, F3-11 조건 저장, F2-7 캘린더 | 알림 구독 수, 알림 메일 클릭률 |
| H2 | 입문자는 공고문 전체 요약보다 "넣기 전에 꼭 알아야 할 것"이 필요하다. 특히 당첨 후 제약이다. | 팀원의 실제 경험("일단 넣고 당첨되면 읽는다" → 당첨 후 포기 페널티를 알고 생각이 바뀜) | F8 당첨 후 제약 카드 | 소수 공개 사용자 인터뷰, 카드의 근거 클릭 여부 |
| H3 | 정정 공고는 놓치기 쉽고, 정정 알림은 기존 서비스에 없는 가치다. | 최근 공고 13%가 정정, 정정해도 API 값은 그대로이고 PDF만 바뀐다. | F1-5·6 정정 감지, F7-3 정정 알림 | 정정 알림 메일 클릭률, 소수 공개 인터뷰 |
| H4 | 원문 근거(쪽 번호·인용 문구)가 붙어 있으면 사용자는 LLM이 정리한 정보를 믿고 쓴다. | 서비스가 판정하지 않으므로 신뢰는 근거에서 나온다. | F6 원문 근거, F5 조건표 | 근거 클릭 여부, 소수 공개 인터뷰 |
| H5 | 입문자에게는 질문형 자가진단 없이 공급 유형별 조건표와 체크박스로 충분하다. | 질문 변환 단계는 오류가 생길 곳을 늘리고 결과가 판정처럼 보인다(기획서 D-10). | F5 조건표 | 소수 공개 인터뷰. 부족하면 런칭 후 질문형을 다시 검토한다. |

**차별점:** H2·H3이 맞다면 청담의 차별점은 "당첨 후 제약을 근거와 함께 미리 보여 주는 것"과 "정정 알림"이다. 6주차 소수 공개에서 기존 서비스(청약홈, 부동산 앱)와 비교해 확인한다.

## 5. 솔루션 제약 조건 및 원칙

### 5.1 원칙

| 원칙 | 내용 |
|---|---|
| **판정이 아니라 안내** | "자격이 됩니다", "신청 가능합니다"라고 단정하지 않는다. 조건과 근거를 보여 주고 판단은 사용자가 한다. 결과를 색이나 점수로 분류하지 않는다. |
| **모든 정보에 원문 근거** | PDF에서 뽑은 항목마다 원문 쪽 번호와 인용 문구를 단다. 인용 문구가 원문에 실제로 있는지 문자열로 검증하고, 확인되지 않은 항목은 "원문 확인 필요"로 표시한다. |
| **공식 API 우선** | 공고 목록과 정형 데이터는 공식 Open API로 받는다. 공고문 PDF 수집처럼 꼭 필요한 곳에만 웹 요청을 쓰고 속도를 제한한다. |
| **개인정보 최소** | 회원가입이 없다. 서버에 저장하는 개인정보는 알림 구독 이메일과 그 이메일의 필터 조건뿐이다. 조건표 체크 상태는 브라우저에만 둔다. |
| **불안을 팔지 않는다** | "놓치지 않고, 후회하지 않게"는 내부 방향이다. 화면 문구에는 "놓치면 후회할" 같은 과장·불안 조장 표현을 쓰지 않는다([기획서 5장](SERVICE_SPEC.md#5-문구-가이드)). |

### 5.2 범위 제약

**포함**
- 공고 종류: 청약홈(한국부동산원)의 APT 분양 공고. 민영주택, 국민주택, 무순위·잔여세대(무순위, 불법행위 재공급).
- 알림 채널: 이메일.

**제외 (향후 확장 후보)**
- LH·SH 공공임대(행복주택, 국민임대, 매입임대), 오피스텔·도시형생활주택 등 APT 외 공고
- 카카오톡 알림톡, 웹 푸시, 모바일 앱
- 회원가입, 프로필 입력, 프로필 기반 맞춤 추천
- 사용자 정보로 자격을 자동 판정하는 기능, 질문형 자가진단(기획서 D-10)
- 가점 계산기(청약홈에 있음), 공고 비교
- 관심 공고 접수 리마인더 메일(캘린더 버튼 클릭률을 보고 런칭 후 결정, 기획서 D-16)

### 5.3 데이터 제약

자세한 조사 결과는 [기술 노트 1~2장](TECH_NOTES.md)에 있다.

- 자격 요건과 당첨 후 제약(재당첨 제한, 전매제한, 실거주 의무, 계약금 등)은 API에 없고 공고문 PDF에만 있다.
- API에는 수정일시·정정 여부 필드가 없다. 정정해도 API 값은 그대로이고 PDF만 바뀔 수 있다.
- 무순위·잔여세대 공고에는 주택 구분(민영/국민)과 특별공급 유형별 세대수가 없다.
- 신혼희망타운(LH 공공분양)은 청약홈에 공고문 PDF가 없다.
- 규제 지역 필드(`SPECLT_RDN_EARTH_AT` 등)는 의미를 추정한 상태라 명세로 확인하기 전에는 화면에 쓰지 않는다(기획서 D-03). 당첨 후 제약은 이 필드가 아니라 공고문 문구를 근거로 쓴다.
- LLM 추출 비용은 일반 APT 공고 1건에 입력만 약 $1~1.5다. 정정되면 처음부터 다시 추출한다.

### 5.4 자원 제약

- 2명, 파트타임(1인당 주 10~15시간). 1주차 실험 이후 남은 5주의 예산은 약 100~150시간이다.
- 바뀐 범위의 추정은 114~176시간으로 예산보다 크다. 그래서 4주차 끝에 밀려 있으면 아래 순서로 자른다([MVP 일정](SCHEDULE.md#컷-순서)).
  1. 원문 자체 뷰어 → 쪽 번호 + 인용문 미리보기 + 청약홈 링크(기획서 D-04 대안)
  2. 정정 알림의 "무엇이 바뀌었나" → "정정됨 + 원문 링크"만
  3. 용어 툴팁 → 특별공급 유형 이름에만
- **자르지 않는 것:** 수집·필터, 알림(새 공고·정정), 조건표, 당첨 후 제약 카드, 원문 근거 표시.

## 6. 핵심 기능 (MVP)

모든 기능이 런칭 조건(필수)이다. 기능 ID는 다른 문서가 참조하므로 바꾸지 않는다.

| 역할 | 기능 | 한 줄 설명 |
|---|---|---|
| 바닥 | **F1. 공고 수집·정정 감지** | 공고와 공고문 PDF를 매일 모으고, 새 공고와 정정을 감지한다. |
| 놓치지 않게 | **F3. 검색·필터·조건 저장** | 지역·유형·접수 상태·특별공급·가격·면적으로 공고를 거르고, 그 조건을 알림용으로 저장한다. |
| 놓치지 않게 | **F7. 관심 조건 알림** | 저장한 조건에 맞는 새 공고와 정정을 이메일로 알린다. |
| 놓치지 않게 | **F2. 공고 상세 요약·일정** | 위치·규모·분양가·일정·정정 이력을 한 화면에 보여 주고 일정을 캘린더에 넣게 한다. |
| 후회하지 않게 | **F8. 당첨되면 이렇게 돼요** | 재당첨 제한, 전매제한, 실거주 의무, 계약금, 부적격 당첨 제한을 근거와 함께 보여 준다. |
| 후회하지 않게 | **F5. 공급 유형별 자격 조건표** | 공급 유형별 자격 조건을 쉬운 문장과 근거로 보여 주고, 줄마다 체크하게 한다. |
| 신뢰 | **F6. 원문 근거·원문 보기** | 근거를 누르면 공고문의 해당 쪽으로 간다. |

### F1. 공고 수집·정정 감지

| ID | 요구사항 |
|---|---|
| F1-1 | 공공데이터포털 「한국부동산원_청약홈 분양정보 조회 서비스」 API로 APT 공고와 무순위·잔여세대 공고를 주기적으로 수집한다. |
| F1-2 | 공고별 주택형 정보(주택형·전용면적, 공급면적, 일반·특별공급 세대수, 특별공급 유형별 세대수, 최고 분양가)를 함께 수집한다. 공고 유형에 따라 API에 없는 항목은 비워 둔다. |
| F1-3 | 공고문 PDF를 수집해 저장한다. |
| F1-4 | 신규 공고를 감지한다. |
| F1-5 | 변경·정정된 공고를 감지한다. API 레코드 해시와 공고문 PDF 파일 해시를 함께 비교한다. |
| F1-6 | 변경이 감지되면 요건 추출을 처음부터 다시 하고, 정정 PDF 첫 쪽의 정정 안내(변경 전/후)에서 무엇이 바뀌었는지 기록한다. |

### F2. 공고 상세 요약·일정

| ID | 요구사항 |
|---|---|
| F2-1 | 공고마다 핵심 정보를 한눈에 보여 준다: 위치, 공급 규모, 주택형별 분양가, 주요 일정(특별공급, 1·2순위 접수, 당첨자 발표, 계약). |
| F2-2 | 공고문 PDF에서 자격 요건과 당첨 후 제약을 구조화해 추출한다(F5, F8의 재료). 「주택공급에 관한 규칙」을 옮긴 일반 규정은 "일반 규정" 묶음으로 따로 둔다. |
| F2-3 | 추출한 항목마다 원문의 쪽 번호와 인용 문구를 함께 저장하고, 인용 문구가 원문에 있는지 검증한다. |
| F2-4 | 필터와 조건표에 나오는 어려운 용어와 특별공급 유형에 툴팁으로 쉬운 설명을 붙인다. 공고 원문이 아닌 일반 설명이므로 "공고마다 다를 수 있음"을 표시한다. 별도 용어 사전 화면은 두지 않는다(기획서 D-13). |
| F2-5 | "최종 확인은 원문 공고문으로 해야 한다"는 안내를 상세 화면에 항상 표시한다. |
| F2-6 | 정정 이력, 무엇이 바뀌었는지, 마지막 확인 시각을 표시한다. |
| F2-7 | 접수일(유형별), 당첨자 발표일, 계약일을 캘린더 파일(.ics)로 내려받게 한다. 공고 상세와 알림 메일에 버튼을 둔다. |

### F3. 검색·필터·조건 저장

| ID | 조건·항목 | 요구사항 |
|---|---|---|
| F3-1 | 지역 | 공급지역(시·도) 기준. 여러 지역을 함께 고를 수 있다. |
| F3-2 | 주택 구분 | 민영주택 / 국민주택 |
| F3-3 | 공고 유형 | 일반 분양 / 무순위 / 불법행위 재공급 |
| F3-4 | 접수 상태 | 접수 예정 / 접수 중 / 마감. 첫 접수 시작일 ~ 마지막 접수 종료일 = 접수 중. |
| F3-5 | 특별공급 유형 | 신혼부부, 생애최초, 다자녀, 노부모, 청년, 신생아 등. 고른 유형의 세대수가 1 이상인 주택형이 있는 공고. |
| F3-6 | 분양가 범위 | 주택형별 최고 분양가 기준 |
| F3-7 | 전용면적 범위 | 주택형별 전용면적 기준. 무순위 공고에는 공급면적이 없어서 전용면적으로 통일한다. |
| F3-8 | 단지명 검색 | 단지명(주택명) 부분 일치 |
| F3-9 | 조건 조합 | 서로 다른 조건은 AND, 한 조건 안의 여러 값은 OR. 주택형 단위 조건(F3-5~F3-7)은 같은 주택형이 모두 만족해야 한다. |
| F3-10 | 정렬 | 기본은 접수 임박순: 접수 중(종료일 가까운 순) → 접수 예정(시작일 가까운 순) → 마감. 모집공고일 최신순도 고를 수 있다. |
| F3-11 | 조건 저장 | 현재 필터 조건을 알림 조건으로 저장한다. 저장은 F7 구독과 함께 이루어진다. |

- 무순위·잔여세대 공고에는 주택 구분(F3-2)과 특별공급 유형별 세대수(F3-5)가 없다. 처리 규칙은 [기획서 P-04](SERVICE_SPEC.md#p-04-정보가-없는-공고)를 따른다.

### F5. 공급 유형별 자격 조건표

| ID | 요구사항 |
|---|---|
| F5-1 | 공고 상세에 이 공고에 있는 공급 유형(특별공급 유형별, 일반공급 1·2순위, 무순위)마다 자격 조건을 쉬운 문장으로 보여 준다. 숫자·기간·비율은 원문 그대로 쓴다. |
| F5-2 | 조건마다 원문 근거(쪽 번호·인용 문구)를 단다. 근거가 확인되지 않은 조건은 "원문 확인 필요"로 표시한다. |
| F5-3 | 조건마다 체크박스를 단다. 체크 상태는 브라우저에만 두고 서버에 보내지 않는다. 체크 결과로 자격을 분류하거나 판정하지 않는다. |

### F6. 원문 근거·원문 보기

| ID | 요구사항 |
|---|---|
| F6-1 | 공고마다 원본 공고문(PDF)과 청약홈 공고 페이지 링크를 제공한다. |
| F6-2 | 근거를 누르면 원문의 해당 쪽으로 이동한다. 저장한 PDF 사본을 자체 뷰어로 보여 주는 것을 기본안으로 하고, 이용 조건상 어렵거나 일정이 밀리면 쪽 번호 + 인용문 미리보기 + 청약홈 링크로 대신한다(기획서 D-04). |

### F7. 관심 조건 알림

| ID | 요구사항 |
|---|---|
| F7-1 | 회원가입 없이 이메일만으로 구독한다. 확인 메일의 링크를 눌러야 구독이 시작된다. |
| F7-2 | 저장한 조건(F3-11)에 맞는 신규 공고가 등록되면 이메일로 알린다. |
| F7-3 | 저장한 조건에 맞는 공고가 정정되면 무엇이 바뀌었는지와 함께 이메일로 알린다. |
| F7-4 | 메일 속 관리 링크로 조건을 고치거나 구독을 해지할 수 있다. |

### F8. 당첨되면 이렇게 돼요

추출 분류 6 "당첨 후 제약"을 화면에 보여 주는 기능이다.

| ID | 요구사항 |
|---|---|
| F8-1 | 공고 상세에서 조건표(F5) 위에 카드로 보여 준다. 항목: 재당첨 제한, 전매제한, 실거주 의무, 계약금·중도금 비율과 납부 일정, 부적격 당첨 시 청약 제한, 중복 청약 제한. |
| F8-2 | 항목마다 원문 근거를 달고, 기간·비율은 원문 그대로 옮긴다. 공고문에 없는 항목은 빼고, 빠진 이유를 지어내지 않는다. |
| F8-3 | 규제 지역 API 필드로 추정하지 않고 공고문 문구를 근거로 쓴다. |

## 7. 사용자 흐름

### 7.1 처음 방문: 찾기 → 확인 → 행동

```
유입(검색·공유 링크) → 공고 목록 → 필터(지역·특별공급 유형 등) → 공고 상세
  → 기본 정보·일정 확인 → "당첨되면 이렇게 돼요" 확인 → 내 공급 유형의 조건표 체크
  → (필요하면) 근거 눌러 원문 해당 쪽 확인
  → 캘린더에 일정 추가 → 접수일에 청약홈에서 신청
```

### 7.2 알림 구독: 조건 저장 → 메일 → 상세

```
공고 목록에서 필터 설정 → "이 조건으로 알림 받기" → 이메일 입력 → 확인 메일의 링크 클릭(구독 시작)
  → 새 공고 알림 메일 → 공고 상세(7.1과 같은 흐름)
  → 정정 알림 메일(무엇이 바뀌었는지) → 공고 상세의 정정 이력
  → 메일 속 관리 링크로 조건 수정·해지
```

화면 단위의 흐름은 [서비스 기획서 2장](SERVICE_SPEC.md#2-사용자-흐름)에 있다.

## 8. 기술 스택과 UI 제약사항

### 8.1 기술 스택

| 영역 | 선택 | 상태 |
|---|---|---|
| 프론트엔드 | React SPA (Vite, TypeScript). 원문 뷰어는 PDF.js | 확정 (2026-10-20) |
| 백엔드 | Spring Boot (Java LTS, Gradle). 공고·구독 API, 메일 렌더링·발송, 공고 상세 URL의 메타 태그. 정확한 버전은 2주차 골격을 만들 때 Spring Initializr의 최신 안정 버전으로 고정한다 | 확정 (2026-10-20) |
| 데이터 배치 | Python. 수집, 정정 감지, PDF 수집, LLM 추출, 알림 대상 매칭 | 확정 (1주차 실험 코드를 이어 씀) |
| LLM | Claude API (claude-opus-5-5). 공고문 PDF를 그대로 넣고 citations로 쪽 번호와 인용 문구를 받는다. citations는 structured outputs와 함께 쓸 수 없어서 정해진 줄 형식의 텍스트로 받는다. | 실험으로 확인 (`experiments/pdf_extraction/extract.py`) |
| 인프라 | 네이버 클라우드 플랫폼(NCP) VM 한 대에 Docker Compose로 모두 올린다. 메모리 4GB 이상 권장 | 확정 (2026-10-20) |
| 이메일 발송 | NCP Cloud Outbound Mailer | 확정 (2026-10-20). 무료 구간·단가는 콘솔 요금 안내에서 확인한다. 2026-09-17 SENS(Simple & Easy Notification Service)로 통합되었다는 안내가 있어 콘솔의 서비스 이름을 함께 확인한다 |
| DB | PostgreSQL (VM의 Docker 컨테이너). 하루 1회 덤프를 NCP Object Storage로 백업 | 확정 (2026-10-20) |
| 웹 서버 | Nginx: React 정적 파일 서빙, Spring 리버스 프록시, HTTPS(Let's Encrypt) | 확정 (2026-10-20) |
| PDF 저장 | VM 디스크. 하루 1회 NCP Object Storage로 백업 | 확정 (2026-10-20) |
| 배치 실행 | VM의 cron이 Python 배치 컨테이너를 실행(P-10, P-17 시각) | 확정 (2026-10-20) |
| 도메인 | `cheongdam.app` (HTTPS 강제 도메인). 메일 발신 도메인 인증(SPF·DKIM)에도 쓴다 | 확정, 등록 예정 (2026-10-20 레지스트리 조회 시 미등록) |

**구성**

```
             ┌──────────────── NCP VM (Docker Compose) ────────────────┐
 사용자 ──▶ │ Nginx ──▶ React 정적 파일                                 │
            │   └──▶ Spring Boot (API, 메타 태그, 메일 발송) ──┐         │
            │                                                 ▼         │
            │ cron ──▶ Python 배치 (수집·감지·추출·매칭) ──▶ PostgreSQL  │
            │                       └──▶ PDF 파일(디스크)                │
            └─────────────────────────────────────────────────────────┘
 Python ──▶ 청약홈 API·첨부파일, Claude API      Spring ──▶ NCP 메일
```

**두 언어가 만나는 방식**

- Python 배치와 Spring은 **DB로만 주고받는다.** 서로의 코드를 호출하지 않는다.
- 알림은 Python이 "누구에게 어떤 공고를 보낼지"를 계산해 **발송 대기 테이블**에 쌓고, Spring이 그 테이블을 읽어 메일을 렌더링하고 보낸다. 메일 템플릿과 발송 서비스 연동은 Spring 한 곳에만 둔다([알림 문서 4장](spec/ALERTS.md#4-알림-정책)).

**선택 이유와 대가**

- **Spring + React:** 팀이 익숙하고 포트폴리오로 보여 주려는 조합이다. 서버가 Spring 하나라서 B의 부담이 가장 작다.
- **React SPA로 인한 검색 노출의 한계:** 서버 렌더링을 하지 않으므로 공고 상세의 본문은 검색 엔진에 잘 노출되지 않는다. MVP에서는 Spring이 `/notices/{공고번호}` 요청에 공고별 제목·설명·OG 태그를 넣은 `index.html`을 돌려주어 공유 미리보기와 기본 검색 노출만 맞춘다. 유입은 알림 메일과 공유 링크가 중심이므로 감수한다.
- **Python 유지:** 1주차 실험 코드(추출, 정정 확인)를 그대로 이어 쓴다.
- **VM 한 대:** 배치 실행과 PDF 저장이 자유롭고 비용이 예측된다. 대신 서버 관리(보안 업데이트, 백업, 디스크)를 직접 한다.
- **NCP 메일:** 예상 발송량(구독자 100명 기준 월 3,000통 안팎)에서는 어느 서비스든 비용이 미미하므로, VM과 같은 클라우드를 써서 계정·결제·콘솔을 하나로 묶는다. VM에서 직접 SMTP로 보내지 않는다(스팸 분류, 포트 차단).

**스택이 지켜야 할 요구 조건**

- 매일 도는 배치 작업(수집, 정정 감지, 요건 추출, 알림 매칭)을 예약 실행할 수 있어야 한다.
- 공고문 PDF 사본을 저장하고 쪽 단위로 보여 줄 수 있어야 한다(F6-2 기본안).
- 공고·주택형·추출 결과·버전 이력을 관계형으로 저장하고, 주택형 단위 조건(F3-9)으로 거를 수 있어야 한다.
- 확인 메일, 알림 메일, 해지 링크를 보낼 수 있어야 한다. 발신 도메인 인증(SPF·DKIM)이 필요하므로 서비스 도메인이 있어야 한다.
- 공고 상세 URL은 공유했을 때 공고 제목과 설명이 미리보기로 보여야 한다.

### 8.3 UI 제약사항과 디자인 콘셉트

- **모바일 우선 반응형 웹.** 기준 폭은 모바일 360px, 데스크톱 1280px이다. 앱은 만들지 않는다.
- **디자인 콘셉트: 차분하고 믿을 수 있는 정보 서비스.** 색과 장식보다 정보 위계(일정 → 당첨 후 제약 → 조건표)를 앞세운다. 근거 칩(`p.34 ›`)은 모든 화면에서 같은 모양으로 쓴다.
- **판정처럼 보이는 UI를 쓰지 않는다.** 초록/빨강 결과 색, 점수, "적합" 배지를 쓰지 않는다.
- **면책 안내를 항상 보인다.** "최종 확인은 원문 공고문으로" 안내를 상세 화면과 푸터에 둔다.
- **말투는 해요체**이며 숫자·날짜는 원문 그대로 쓴다. 자세한 규칙은 [기획서 5장](SERVICE_SPEC.md#5-문구-가이드)에 있다.
- 지원 브라우저: 최신 Chrome, Safari(iOS 16+), Samsung Internet, Edge.
