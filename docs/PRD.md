# PRD: 청약 공고 요약·맞춤 탐색 서비스 (가칭 "청담")

- 작성일: 2026-10-06
- 상태: 초안 (탐색 세션 결과 정리)
- 범위: MVP

---

## 1. 배경과 문제

청약 공고는 계속 새로 등록되고 정정되지만, 공고문 하나가 수십 페이지 분량이고 용어와 조건이 복잡하다.
청약에 익숙하지 않은 사용자는 다음 단계마다 막힌다.

1. **발견:** 어떤 공고가 새로 나왔는지, 무엇이 바뀌었는지 계속 확인해야 한다.
2. **이해:** 공고문의 핵심(일정, 공급 규모, 분양가, 자격 요건)을 파악하기 어렵다.
3. **판단:** "이 공고에 내가 신청할 수 있나?"를 스스로 판단하기 어렵다.

## 2. 목표

사용자가 공고문을 매번 직접 찾아 읽고 비교하지 않아도, **자신과 관련 있는 공고를 빠르게 발견하고, 쉬운 말로 이해하고, 신청 가능 여부를 스스로 점검**할 수 있게 한다.

### 프로젝트 성격
- 포트폴리오이면서 실제로 런칭해 사용자 반응도 확인하는 것이 목표다.
- 따라서 기술적으로 깊이 있는 부분(수집 파이프라인, PDF·LLM 추출, 원문 근거 표시)을 제대로 만들면서도, 실제 운영에 필요한 최소한의 안정성과 개인정보 보호를 갖춘다.

## 3. 대상 사용자

**주 사용자: 청약 입문자**
- 사회초년생, 신혼부부 등 청약을 처음 알아보는 사람
- '특별공급', '해당지역 우선', '무주택세대구성원' 같은 용어부터 낯설다.
- 원하는 것: "나와 관련 있는 공고가 뭔지", "이 공고가 무슨 내용인지", "나도 신청할 수 있는지"

**MVP에서 우선순위가 낮은 사용자:** 이미 청약을 잘 아는 사람. 이들에게는 빠른 알림과 비교가 핵심이며, 이 니즈는 MVP 이후에 강화한다.

## 4. 핵심 설계 원칙

| 원칙 | 내용 |
|---|---|
| **판정이 아니라 안내** | 서비스는 "당신은 자격이 됩니다"라고 단정하지 않는다. 사용자가 원문을 바탕으로 스스로 판단하도록 돕는다. |
| **모든 요약에 원문 근거 표시** | 요약·요건 항목마다 공고문의 해당 페이지와 문구를 연결한다. 사람이 검수하지 않고 자동으로 운영하되, 사용자가 언제든 원문으로 확인할 수 있게 한다. |
| **2층 판정 구조** | 1층은 프로필 기반 필터링(관련 있을 법한 공고 추리기), 2층은 공고별 자가진단(요건을 하나씩 직접 체크)이다. |
| **공식 API 우선** | 공고 목록과 정형 데이터는 공식 Open API로 받는다. 스크래핑은 공고문 PDF 수집처럼 꼭 필요한 곳에만 쓴다. |

## 5. MVP 범위

### 포함
- **공고 종류:** 청약홈(한국부동산원)의 **APT 분양 공고**
  - 민영주택, 국민주택
  - 무순위·잔여세대
- **알림 채널:** 이메일

### 제외 (향후 확장 후보)
- LH·SH 등 공공임대(행복주택, 국민임대, 매입임대)
- 오피스텔·도시형생활주택 등 APT 외 공고
- 카카오톡 알림톡, 웹 푸시, 모바일 앱
- 가점 계산기 (청약홈에 이미 있음)
- 프로필만으로 자격을 자동 판정하는 기능

## 6. 기능 요구사항

### F1. 공고 수집·갱신
| ID | 요구사항 |
|---|---|
| F1-1 | 공공데이터포털 「한국부동산원_청약홈 분양정보 조회 서비스」 API로 APT 공고와 무순위·잔여세대 공고를 주기적으로 수집한다. |
| F1-2 | 공고별 주택형 정보(주택형, 공급면적, 일반·특별공급 세대수, 특별공급 유형별 세대수, 최고 분양가)를 함께 수집한다. |
| F1-3 | 공고문 PDF를 수집해 저장한다. |
| F1-4 | 신규 공고를 감지한다. |
| F1-5 | 변경·정정된 공고를 감지한다. API에 수정일시 필드가 없으므로, 최근 N일 범위를 주기적으로 다시 조회하고 공고 키별 레코드 해시를 비교하는 방식으로 감지한다. |
| F1-6 | 변경이 감지되면 요약과 요건 추출을 다시 수행하고, 무엇이 바뀌었는지 기록한다. |

### F2. 공고 요약 (원문 근거 포함)
| ID | 요구사항 |
|---|---|
| F2-1 | 공고마다 핵심 정보를 한눈에 보여준다: 위치, 공급 규모, 주택형별 분양가, 주요 일정(특별공급, 1·2순위 접수, 당첨자 발표, 계약), 규제 지역 여부. |
| F2-2 | 공고문 PDF에서 자격 요건(특별공급 유형별 조건, 소득·자산 기준, 거주지 우선순위, 무주택 요건, 청약통장 요건 등)을 구조화해 추출한다. |
| F2-3 | 추출한 항목마다 원문의 페이지 번호와 근거 문구를 함께 저장하고 보여준다. |
| F2-4 | 어려운 청약 용어에는 쉬운 말 설명을 붙인다(용어 툴팁 또는 용어집). |
| F2-5 | "최종 확인은 원문 공고문으로 해야 한다"는 안내를 요약 화면에 항상 표시한다. |

### F3. 검색·필터링
| ID | 요구사항 |
|---|---|
| F3-1 | 지역, 주택 구분(민영/국민), 공고 유형(일반/무순위·잔여세대), 접수 상태(접수 예정/접수 중/마감)로 필터링한다. |
| F3-2 | 특정 특별공급 유형(신혼부부, 생애최초, 다자녀, 노부모, 청년, 신생아 등)이 포함된 공고로 필터링한다. |
| F3-3 | 분양가 범위와 공급면적 범위로 필터링한다. |
| F3-4 | 단지명으로 검색한다. |

### F4. 프로필 기반 맞춤 공고 (1층)
| ID | 요구사항 |
|---|---|
| F4-1 | 사용자가 간단한 프로필(관심 지역, 결혼·자녀 여부, 무주택 여부, 대략적인 연령대 등)을 입력할 수 있다. |
| F4-2 | 프로필을 바탕으로 **명백히 해당되지 않는 공고는 거르고**, 관련 있을 법한 공고와 해당될 수 있는 특별공급 유형을 강조해 보여준다. |
| F4-3 | 맞춤 결과는 "신청 가능"이 아니라 "관련 있을 수 있음"으로 표현한다. |

### F5. 공고별 자가진단 (2층)
| ID | 요구사항 |
|---|---|
| F5-1 | 공고에서 추출한 자격 요건을 쉬운 예/아니오 질문 형태의 체크리스트로 보여준다. |
| F5-2 | 체크리스트 항목마다 원문 근거(페이지·문구)를 연결한다. |
| F5-3 | 사용자의 응답에 따라 지원을 검토해 볼 만한 공급 유형(특별공급 유형, 일반공급 순위)을 정리해 보여준다. 단, 최종 판정이 아니라는 점을 명시한다. |
| F5-4 | 프로필에 이미 입력한 정보는 체크리스트에 미리 채워 둔다. |

### F6. 원문 확인
| ID | 요구사항 |
|---|---|
| F6-1 | 공고마다 원본 공고문(PDF)과 청약홈 공고 페이지 링크를 제공한다. |
| F6-2 | 요약·체크리스트에서 근거를 누르면 원문의 해당 페이지로 이동한다. |

### F7. 관심 조건 알림
| ID | 요구사항 |
|---|---|
| F7-1 | 사용자가 관심 조건(지역, 공고 유형, 특별공급 유형 등)을 저장할 수 있다. |
| F7-2 | 저장한 조건에 맞는 신규 공고가 등록되면 이메일로 알린다. |
| F7-3 | 관심 공고가 정정되면 무엇이 바뀌었는지와 함께 이메일로 알린다. |
| F7-4 | 이메일에서 알림을 쉽게 해지할 수 있다. |

## 7. 데이터 출처 (조사 결과)

**공식 API:** 「한국부동산원_청약홈 분양정보 조회 서비스」 (https://www.data.go.kr/data/15098547/openapi.do)
- REST(JSON/XML), `serviceKey` 인증, 무료
- 개발계정 트래픽 40,000건. 운영계정은 활용사례를 등록하면 늘릴 수 있다.
- 사용할 오퍼레이션
  - `getAPTLttotPblancDetail` / `getAPTLttotPblancMdl`: APT 공고 / 주택형별 정보
  - `getRemndrLttotPblancDetail` / `getRemndrLttotPblancMdl`: 무순위·잔여세대 공고 / 주택형별 정보
- API로 받을 수 있는 것
  - 공고: 공급지역, 모집공고일, 접수 일정, 당첨자 발표일, 계약일, 규제 여부, 홈페이지 주소, 공고 URL
  - 주택형별: 세대수, 특별공급 유형별 세대수, 최고 분양가
- **API로 받을 수 없는 것:** 자격 요건(소득 기준, 거주지 우선, 특별공급 세부 조건)은 공고문 PDF에만 있다.
- **정정 공고:** 수정일시나 정정 여부 필드가 없다. 해시 비교로 감지해야 한다.

## 8. 기술 고려사항

- **PDF → 구조화 추출 파이프라인이 서비스의 핵심이다.**
  - 파싱할 때 페이지와 위치 정보를 유지해야 원문 근거를 표시할 수 있다.
  - LLM이 각 항목의 근거(페이지·문구)를 함께 출력하도록 추출 스키마를 정의한다.
  - 근거 문구가 실제로 원문에 있는지 문자열 매칭으로 검증하고, 근거가 확인되지 않는 항목은 표시하지 않거나 "확인 필요"로 표시한다.
- 공고문 PDF 형식(텍스트 PDF인지 이미지 스캔인지, 표 구조 등)이 공고마다 다를 수 있다.
- 정정 공고를 처리하려면 공고마다 버전 이력을 남겨야 한다.
- 개인정보: 프로필 정보(결혼 여부, 무주택 여부 등)는 민감할 수 있다. 수집 항목을 최소화하고, 소득처럼 민감한 값은 저장하지 않고 자가진단 중에만 쓰는 방식을 검토한다.

## 9. 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| LLM 추출 오류(잘못된 소득 기준 등) | 사용자가 잘못 판단해 기회를 놓치거나 부적격 신청 | 원문 근거 표시, 근거 문자열 검증, "최종 확인은 원문으로" 안내 |
| 공고문 PDF 형식이 제각각 | 추출 실패나 품질 편차 | 실패 시 요약 없이 기본 정보와 원문 링크만 제공, 실패율 모니터링 |
| 정정 공고 감지 누락 | 오래된 정보 제공 | 감지 범위(N일)와 주기 조정, 공고 상세 화면에 마지막 확인 시각 표시 |
| 공공기관 사이트 PDF 수집의 약관·부하 문제 | 차단, 법적 리스크 | 공식 API 우선, PDF 요청은 최소화하고 속도 제한 적용 |
| API 트래픽 한도 | 수집 중단 | 운영계정 전환, 증분 수집 |

## 10. 성공 지표 (제안)

- 신규 공고가 등록되고 서비스에 노출되기까지 걸리는 시간
- 공고문 PDF 요약·요건 추출 성공률과, 샘플 검수 기준 정확도
- 자가진단을 끝까지 완료한 비율
- 알림 구독자 수와 알림 이메일 클릭률
- 재방문율

## 11. 미해결 질문

1. 정정 공고가 같은 공고번호로 덮어써지는가, 새 번호로 따로 등록되는가? (실데이터로 확인 필요)
2. API의 `PBLANC_URL`에서 공고문 PDF를 바로 받을 수 있는가, 아니면 별도 다운로드 절차가 필요한가?
3. 공고문 PDF는 대부분 텍스트 PDF인가, 표와 이미지가 많은가? 어떤 파싱 방식이 적합한가?
4. 프로필 입력 항목을 어디까지 받을 것인가? (편의성과 개인정보 사이의 균형)
5. 회원가입 없이 이메일만으로 알림을 구독하게 할 것인가?
6. 기존 서비스(청약홈 앱, 부동산 앱 등)의 알림·요약 기능과 비교해 차별점을 검증해야 한다.

## 12. 향후 확장 후보

- LH·SH 공공임대 공고 (입문자인 청년·신혼부부에게 현실적인 선택지가 많음)
- 카카오톡 알림톡, 웹 푸시
- 공고 간 비교 기능 (청약을 잘 아는 사용자 대상)
- 반복되는 요건 규칙의 자동 판정 (자가진단 데이터가 쌓인 뒤)
