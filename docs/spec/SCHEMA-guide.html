청담 DB 스키마 가이드

근거: V1__init.sql · docs/spec/SCHEMA.md · dev-seed.sql. 점선 밑줄 단어는 마우스를 올리거나 탭하면 청약 용어 설명이 나와요.

13개 테이블, 5개 영역

청담은 A(Python)가 청약홈 데이터를 모으고 PDF를 읽어 DB에 쓰고, B(Spring)가 그것을 화면·메일로 내보내요. 둘은 DB로만 대화해요. 그래서 "테이블마다 쓰는 쪽이 한 명"이 핵심 규칙이에요.

A(Python)가 씀B(Spring)가 씀A가 적재 + B가 상태 갱신

테이블 관계

1─N은 "하나에 여러 개"예요. 예: 공고 1개에 주택형 여러 개.

notice ─1──N─ notice_schedule (접수·당첨·계약 일정) ─1──N─ notice_unit (주택형: 59㎡, 84㎡ …) ─1──N─ notice_version ─1──N─ notice_change (정정 이력) ─1──1─ extraction_run ─1──N─ extracted_item ─1──N─ item_evidence (버전마다 한 번 추출) (요건 한 줄) (원문 근거) subscription ─1──N─ alert_outbox ─1──N─ alert_outbox_notice ──▶ (notice, version) ─1──N─ alert_log 발송 이력 crawl_run (독립: 수집 실행 일지)

이 설계를 읽는 6가지 열쇠

  1. 접수 "상태"는 저장하지 않아요. 접수 시작·종료일만 저장하고, 접수 예정/접수 중/마감은 조회할 때 오늘 날짜와 비교해 계산해요. 저장해 두면 자정마다 갱신해야 해서요.
  2. "정보 없음(NULL)"과 "0"은 달라요. 무순위 공고는 청약홈이 특별공급 유형별 세대수를 안 줘서 NULL, 일반 분양에서 신혼부부 몫이 없으면 0이에요. 필터가 NULL 공고를 제외하고 안내 배너를 띄우는 기준이에요.
  3. 정정은 덮어쓰지 않고 버전을 쌓아요. notice는 항상 최신 값, 과거는 notice_version·notice_change에 남아요.
  4. 원문(raw)을 같이 보관해요. API 응답을 통째로 jsonb로 저장해 두면 해시 비교로 정정을 감지하고, 가공 규칙이 바뀌어도 다시 계산할 수 있어요.
  5. AI가 뽑은 요건에는 항상 근거가 붙어요. item_evidence에 쪽 번호와 인용문이 있고, 그 문구가 실제 원문에 있는지 검증한 결과(verified)가 저장돼요.
  6. 개인정보는 subscription.email 하나뿐이에요. 해지·미확인이면 바로 지워요.

모든 예시는 개발 시드 공고 DEV001 「○○자이 더 센트럴」(경기 수원, 민영, 812세대, 정정 1회)을 따라가요. 날짜는 시드를 돌린 날(2026-10-22) 기준이에요. 표를 펼쳐서 보세요.

시나리오를 고르면 그 순간 읽는 테이블(보라)과 쓰는 테이블(빨강)이 지도에 표시돼요.
