## 전제와 현실 점검

- 총 가용 시간은 약 **120~180시간**(2명 × 주 10~15시간 × 6주)이다. PRD의 기능을 모두 완성도 있게 만들기에는 빠듯하다.
- 그래서 **우선순위와 컷 라인**을 미리 정해 둔다(PRD 6장과 같다). 일정이 밀리면 "후순위" 기능부터 런칭 이후로 미룬다.

| 구분 | 기능 |
|---|---|
| 필수 (런칭 조건) | F1 공고 수집·갱신, F2 요약(원문 근거 포함), F3 검색·필터링, F6 원문 확인 |
| 중요 | F5 공고별 자가진단 (2단계: 자격 점검) |
| 후순위 (밀리면 런칭 이후) | F3-11 필터 조건 저장, F7 이메일 알림 |

- 가장 큰 리스크는 **PDF에서 자격 요건을 뽑아내는 품질**이다. 그래서 1주차에 먼저 실험해 보고 진행 여부를 판단한다.

## 역할 분담

| 담당 | 영역 | 주요 기능 |
|---|---|---|
| **A: 데이터** | 수집 파이프라인, PDF 파싱, LLM 추출 | F1, F2(추출), F5(체크리스트 데이터) |
| **B: 서비스** | 백엔드 API, 프론트엔드, 알림, 배포 | F2(화면), F3, F5(화면), F6, F7 |

- 두 영역은 **DB 스키마와 추출 결과 JSON 스키마**에서 만난다. 이 두 가지는 1주차에 함께 정하고, 바꿀 때는 서로 합의한다.
- 역할은 고정이 아니다. 한쪽이 밀리면 다른 쪽이 돕는다.

## 주차별 일정

### 시작 전 (킥오프, 1~2일)
- [ ] 기술 스택 결정 (언어·프레임워크, DB, 배포 환경, LLM 제공자)
- [ ] 공공데이터포털 API 활용신청 (승인까지 시간이 걸릴 수 있으니 가장 먼저)
- [ ] PRD 미해결 질문 5 결정: 회원가입 없이 이메일만으로 구독할지 (F3-11, F7에 영향)
- [ ] 협업 규칙 정하기: 브랜치·PR 리뷰 방식, 이슈 관리(GitHub Issues/Projects), 정기 회의 시간

### 1주차: 실험과 기반 다지기
| A: 데이터 | B: 서비스 |
|---|---|
| API 호출 실험: 실제 응답 확인, PRD 미해결 질문 1·2·4(정정 공고 번호 처리, PDF 다운로드 방법, 필터용 필드) 확인 | 프로젝트 골격 구성(저장소 구조, 백엔드·프론트 초기 세팅) |
| 공고문 PDF 5~10개로 LLM 추출 실험: 요건과 원문 근거(페이지·문구)를 함께 뽑을 수 있는지 (미해결 질문 3) | 주요 화면 와이어프레임(목록, 상세, 자가진단) |

- **함께:** DB 스키마, 추출 결과 JSON 스키마 확정
- **주말 판단:** 추출 품질이 쓸 만한가? 부족하면 F2·F5의 범위를 조정한다(예: 일정·공급 정보 요약을 먼저 하고, 자격 요건 추출은 일부 항목만).

### 2주차: 수집과 목록 화면
| A: 데이터 | B: 서비스 |
|---|---|
| 주기적 수집 배치, DB 저장 | 공고 목록·상세 조회 API |
| 신규·변경 공고 감지(해시 비교), 공고 버전 이력 | 공고 목록 화면, 필터·검색(F3) |

- **산출물:** 실제 공고가 매일 수집되고 목록에서 필터링할 수 있다.

### 3주차: 요약과 원문 근거
| A: 데이터 | B: 서비스 |
|---|---|
| PDF 수집 → 파싱 → LLM 추출 파이프라인 | 공고 상세 화면: 핵심 정보 요약, 주요 일정, 정정 이력·마지막 확인 시각(F2-6) |
| 근거 문구가 원문에 실제로 있는지 검증, 추출 실패 처리 | 근거를 누르면 원문 해당 페이지로 이동(F6), 용어·특별공급 유형 설명(F2-4) |

- **산출물:** 공고를 열면 쉬운 요약과 원문 근거를 볼 수 있다. **필수 기능 완성 목표 시점이다.**

### 4주차: 자가진단
| A: 데이터 | B: 서비스 |
|---|---|
| 추출한 요건을 예/아니오 질문 체크리스트로 변환 | 자가진단 화면(F5) |
| 실제 공고 샘플로 추출 품질 점검과 개선 | (여유가 있으면) 필터 조건 저장(F3-11) |

- **산출물:** 공고 하나를 골라 체크리스트로 자격 요건을 점검할 수 있다.

### 5주차: 알림과 안정화
| A: 데이터 | B: 서비스 |
|---|---|
| 운영 안정화: 실패 재시도, 로그, 추출 실패율 모니터링 | (여유가 있으면) 이메일 알림 구독·발송·해지(F7) |
| 정정 시 바뀐 항목 요약 데이터 생성(F2-6 상세, F7-3) | 운영 환경 배포 준비 |

- **산출물:** 운영 환경에 배포할 준비가 끝난다. 알림은 여유가 있을 때만 포함한다.

### 6주차: 통합과 런칭
- **함께:**
  - [ ] 전체 흐름 통합 테스트
  - [ ] 실제 공고로 요약·요건 정확도 샘플 검수
  - [ ] 면책 안내("최종 확인은 원문으로"), 개인정보처리방침 준비
  - [ ] 배포 후 지인 등 소수 사용자에게 먼저 공개하고 피드백 수집 (PRD 미해결 질문 6 차별점 검증)

## 협업 리듬 (제안)

주 1회 정기 회의(30~60분, 데모와 컷 라인 조정), 평소에는 이슈·PR·메신저로 비동기 공유, PR은 서로 리뷰, 진행 상황은 "이번 주 끝에 무엇을 시연할 수 있는가"로 판단한다.
